Audit date: 2026-09-13. Scope: `packages/astrology-core/` as committed at Phase 1 (`33209ea`) and Phase 2 (`6cde9f0`), plus one fix applied and committed during this gate (`a43ff36`). Method: direct re-reading of the actual shipped source (not memory of having written it), targeted execution against real ICU/tzdata data, and a full re-run of the test suite. No Phase 3 code, no Swiss Ephemeris/pysweph/pyswisseph, no architecture redesign was implemented.

Phase 3 (Western-only calculation, per `ROADMAP.md`) can safely begin on top of the current `BirthData → Timezone/DST → AstronomicalProvider → NormalizedChart` contracts, **provided** the `AstronomicalProvider.CelestialBody` extensibility gap (below) is resolved before Western dignity/Chiron work needs it, and the false `MIN_YEAR` justification is corrected. One confirmed **NormalizedChart-contract-level defect** (`DignityType` accidentally assumes Western astrology) does **not** block Phase 3 itself (Western dignity work only, per the frozen Phase 3 scope) but **is an ARCHITECTURE DECISION REQUIRED before Phase 4 (Vedic)** and should not be deferred silently.

## 1. Executive Summary

Phase 1 and Phase 2 are substantially sound: 108→113 tests pass, the layering is clean, no Swiss Ephemeris dependency exists, and the Western/Vedic-compatibility claims for `NormalizedChart` hold up under adversarial testing (two full fixtures, one Western one Vedic, validate through the exact same code path with identical key sets). One **severe, execution-confirmed bug** was found in the Timezone/DST engine — the one component whose entire purpose is "never silently misinterpret a birth time" — and has been fixed and regression-tested during this gate. One **real contract-level Western-coupling defect** was found in `NormalizedDignityResult.type` (Phase 2), which was correctly left unfixed per the explicit "do not redesign silently" instruction and is reported here for a deliberate decision. Two smaller, non-blocking gaps (`CelestialBody` not extensible; `MIN_YEAR`/`MAX_YEAR` bound justified by a claim that does not hold up under testing) round out the concrete findings.

## 2. Phase 1 Findings (BirthData → Validation → Timezone/DST → AstronomicalProvider)

**BirthData contract**: sound. Pure data, zero business logic, `locationLabel` correctly never touches calculation. `local_time: null` (unknown birth time) is a first-class, tested, non-error state. **One finding**: `validateBirthData`'s `MIN_YEAR = -4712` is justified in its own code comment as "the lower bound of calendar-core's Julian Day algorithm — dates before this cannot compute a positive JDN." This was tested directly against the actual shipped `calendar-core` and found **false**: `isValidCalendarDate(-10000, 3, 12)` returns `true`, and `isValidCalendarDate(10000, 3, 12)` (above the claimed `MAX_YEAR = 9999`) also returns `true`. calendar-core's JDN formula has no such floor/ceiling. **This is a concrete defect**: an artificial validation boundary justified by an incorrect technical claim. Practical impact is low (no real user enters a birth year of ±10,000), but the comment actively misleads future maintainers and the bound itself is unverified. **Proposed minimal fix** (not implemented — reported only, since it's a Phase 1 behavior change, however small): either remove the numeric bound and rely solely on `isValidCalendarDate`'s own round-trip check, or keep a bound but document it honestly as "a practical product-scope limit," not an algorithmic one.

**Timezone/DST engine — SEVERE DEFECT FOUND AND FIXED.** `resolveLocalTimeToUtc` detects ambiguous (fall-back) and nonexistent (spring-forward) local times by sampling the UTC offset ±12 hours around the "naive UTC" point (the local wall-clock numbers interpreted as if they were already UTC). This works correctly for common timezones (Vietnam, US, EU — all tested, all correct) but **was proven, by direct execution, to silently fail for large-offset DST zones**: for `Pacific/Chatham` (offset +12:45/+13:45), local times `02:45`–`03:44` on 2024-09-29 (the real, IANA-documented nonexistent window during that zone's spring-forward) were incorrectly returned as `"resolved"` with a stale pre-transition offset, instead of `"nonexistent"`. Root cause: the ±12h sampling window, anchored on the *naive* (offset-uncorrected) point, can land entirely on one side of the real transition when the zone's offset is large — exactly the "silently reinterprets an invalid local time" failure mode this audit was instructed to hunt for. **Fixed** (commit `a43ff36`): the sampling window is now anchored on `calendar-core`'s own `Timezone.zonedTimeToUtc()` estimate (already offset-corrected via 2-step convergence) instead of the raw naive point. Verified to the minute against the real Chatham transition; 5 regression tests added (113/113 total tests now pass). This fix changes no exported type or function signature — it is a pure internal-implementation correction, not an architecture change, so it did not require a STOP.

Seconds/milliseconds: `LocalTime.second` is typed and validated as a fractional number (`0–59.999...`), but `Date.UTC(...)` (used internally) **silently truncates fractional seconds to whole seconds** — confirmed by direct execution (`Date.UTC(2024,0,1,12,30,45.678)` → `...:45.000Z`). This is a genuine inconsistency between what validation promises and what resolution delivers, though the practical astrological impact is negligible (sub-second birth-time precision is never meaningfully available; 1 second of Moon motion ≈ 0.0002°). **Reported, not fixed** — proposed options: pass the fractional remainder as `Date.UTC`'s milliseconds argument to preserve full precision, or restrict `LocalTime.second` to integers and update the validation message accordingly.

Midnight boundaries, negative/positive offsets, UTC itself, before/after DST, historical timezone changes (Vietnam's 1960 UTC+8 → 1985 UTC+7 change): all directly tested against real ICU data, all correct. Determinism: confirmed by dedicated reproducibility tests; the engine performs no hidden mutable-state access.

**AstronomicalProvider boundary**: correctly abstract from Swiss Ephemeris — nothing in the interface or its supporting types references any ephemeris library. `HouseSystemId`/`AyanamsaId` are open `string` types (no house-system or ayanamsa is hardcoded). **One real gap**: `CelestialBody` is a **closed** 10-value union (`sun`…`pluto`), even though the frozen `DOMAIN_MODEL.md` §3 explicitly lists it as `Sun | Moon | ... | Pluto | Chiron | ... (extensible, not exhaustive at Phase 1)` — Chiron is named in the frozen spec and is absent from the implementation, and the type provides no extension mechanism at all (contradicting the frozen spec's own "extensible" framing). This is a genuine interface-shape defect per Audit 3's explicit instruction to check for "accidental coupling to... a particular [set of bodies]." **Per this task's explicit instruction not to redesign `AstronomicalProvider` silently, this was reported, not fixed.** It does not block Phase 3's minimum scope (Western `core` only needs Sun→Pluto per `WESTERN_AUDIT.md`), but will block the moment Chiron, asteroids, or Vedic-specific points are needed — recommend resolving before or very early in Phase 3, not deferred to Phase 4. **ARCHITECTURE DECISION REQUIRED**, options: (a) widen to a hybrid literal-union-plus-open-string (`"sun" | ... | "pluto" | "chiron" | (string & {})`, preserves autocomplete, still extensible), (b) make it a plain open `string` matching `HouseSystemId`'s pattern (simplest, loses autocomplete), (c) add currently-missing named bodies (`chiron` at minimum) to the closed union and accept that future additions require a (backward-compatible, additive) type change. Recommendation: (a).

## 3. Phase 2 Findings (NormalizedChart)

Structurally sound: `validateNormalizedChart` checks ranges/enums/duplicates without recomputing astrological truth (correctly staying a data contract, not a calculator, as required). `houseCusps` correctly enforces "exactly 12 or exactly 0" (unknown-time chart), not partial. `isRetrograde` consistency with `speedDegreesPerDay`'s sign is enforced. Serialization is genuinely deterministic (verified: key-sorted recursively, `Date` handled explicitly, round-trip tested for both Western and Vedic fixtures).

**Confirmed contract-level defect — accidentally assumes Western astrology.** `NormalizedDignityResult.type` is a **closed union**: `"domicile" | "exaltation" | "detriment" | "fall" | "triplicity" | "term" | "decan"` — this is exclusively Hellenistic/Western traditional-astrology vocabulary (matches `western.traditional`'s Phase-3.1+ scope exactly). Vedic dignity uses an entirely different taxonomy (own sign/moolatrikona/exalted/debilitated/friend/great-friend/neutral/enemy/great-enemy — a 5-tier relationship scale, not a 1:1 mapping to Western terms). **There is currently no way to populate `dignities[]` with a Vedic dignity result at all** without either abusing a Western label to mean something else (semantically wrong) or leaving `dignities[]` permanently empty for Vedic charts (functionally incomplete). This is exactly the "accidentally assumes Western astrology" defect Audit 4 was explicitly instructed to look for in this exact field. **This changes the NormalizedChart contract — per the Architecture Decision Rule, this was reported and NOT silently fixed.**

**ARCHITECTURE DECISION REQUIRED**: how should `NormalizedDignityResult.type` represent multiple schools' dignity taxonomies? Options: (a) make `type` an open `string` (matching `AspectType`'s already-established pattern) with each school defining its own vocabulary via its `dignity_rules` config — simplest, fully consistent with `ADR-003` school isolation, loses compile-time autocomplete for Western consumers; (b) keep a closed Western union for `type` but add a **second**, separate closed (or open) field for non-Western dignity systems, e.g. `vedicType?: "own_sign" | "moolatrikona" | ...` — preserves autocomplete both ways, but starts down a path of one field per school, which cuts against a single generic contract; (c) generalize to a `{system: SchoolId; type: string; score: number}` shape where `type`'s valid values are defined per-`system`, not globally. **Recommendation: (a)**, for direct consistency with how `AspectType`, `HouseSystemId`, `AyanamsaId`, and `SchoolId` are already handled in this exact same file — `dignities[].type` is the one field that didn't follow the pattern already established elsewhere in the same `types.ts`.

**Non-blocking items carried forward correctly** (already flagged in `FUTURE_WORK.md` from Phase 2, re-confirmed still accurate on re-read): ayanamsa numeric value not captured (name only); Dasha/Varga correctly excluded from `NormalizedChart` (belongs to a future, separate data structure).

**Minor serialization hardening gap** (not blocking): `serializeNormalizedChart()` does not require or check that its input already passed `validateNormalizedChart()`. Native `JSON.stringify` (used internally) silently converts `NaN`/`Infinity`/`-Infinity` to `null` — confirmed by direct execution. In the current pipeline this is unreachable in practice (nothing constructs an invalid chart and serializes it without validating first), but nothing in the code enforces that discipline. Recommendation (optional, low priority): document as a required caller convention, or have `serializeNormalizedChart` assert-check for non-finite numbers and throw loudly rather than silently degrading them to `null`.

## 4. Cross-Phase Findings (BirthData → resolveBirthDataInstant → AstronomicalProvider → future Chart Calculation → NormalizedChart)

1. **Can a future provider produce everything NormalizedChart needs?** Mostly yes, with the one confirmed gap: `CelestialBody`'s closed union means a provider literally cannot be asked for Chiron today, even though `NormalizedPlanetPosition.body` (Phase 2) is already an open `string` ready to receive it. This is the same underlying gap as Phase 1 finding above, now confirmed as a real cross-phase mismatch, not just an isolated Phase 1 concern: **Phase 2 already accepts more than Phase 1 can currently produce.**
2. **Is AstronomicalProvider exposing information Phase 2 cannot represent?** No — every provider return shape (`PlanetPosition`, `NodePosition`, `HouseCusps`, `AngleResult`) maps cleanly onto a corresponding, richer Phase 2 type.
3. **Coordinate system mismatch?** None found — both layers consistently use ecliptic longitude/latitude in degrees, `[0,360)` for longitude, `[-90,90]` for latitude, throughout.
4. **Longitude/latitude convention consistency?** Consistent across both phases and enforced by Phase 2's validator.
5. **Retrograde representation consistency?** Consistent: both layers define `isRetrograde` as exactly `speedDegreesPerDay < 0`, and Phase 2 additionally *enforces* this invariant at validation time (`INCONSISTENT_RETROGRADE_FLAG`) — Phase 1 does not enforce it (the provider interface has no validation of its own, by design, since it's just a type contract) but this is not a gap since real enforcement correctly lives at the consuming layer.
6. **Time instants represented consistently?** Yes — `Date` objects throughout, ISO 8601 on serialization, no string/number time representation drift found.
7. **Precision consistent?** Yes — both layers use unrounded double-precision floats; rounding only exists in `precision.ts::roundForDisplay`, explicitly documented as display-only and never used internally by either phase.
8. **Can deterministic golden fixtures be built later?** Yes — confirmed directly: Phase 2's own test fixtures (`fixtures.ts`) already reuse the exact benchmark numbers from `docs/astrology-module/AUDIT/BENCHMARK.md`, and `serializeNormalizedChart`'s determinism is tested and holds.

## 5. Western Compatibility

Verified via `chart/__tests__/schoolCompatibility.test.ts` (already existing from Phase 2, re-run and re-read during this audit, not newly written): a full Western fixture (tropical, Placidus, `school: "western"`) validates through the exact same `validateNormalizedChart()` used for Vedic, with no branch. ## 6. Vedic Compatibility

Same test proves the Vedic fixture (sidereal, Lahiri, whole-sign, `school: "vedic"`) validates identically. **However**, this audit found that "validates" is not the same as "fully expressive": the `dignities[]` field (finding in §3 above) cannot yet correctly represent Vedic dignity results. Divisional charts (Varga) and Dasha are correctly recognized (in `FUTURE_WORK.md`, re-confirmed accurate) as needing their own structure outside `NormalizedChart` — this is not a defect, it's a correct scope boundary already documented.

## 7. Serialization / Reproducibility Findings

`stableStringify` recursively sorts object keys, explicitly converts `Date` to ISO 8601, uses no locale-dependent formatting (`toLocaleString` grep returned zero matches). Confirmed by direct execution: `undefined` object properties are correctly omitted (native `JSON.stringify` behavior, relied on deliberately, confirmed still correct after passing through the custom sort step). `NaN`/`Infinity`/`-Infinity` silently become `null` (native behavior, not specially handled — see §3 minor gap). Two equivalent `NormalizedChart` objects (same values, different field insertion order, different object references) are confirmed, by direct test, to serialize to byte-identical strings. Round-trip (`serialize` → `deserialize`) preserves `Date` as a real `Date` instance, not a string, for both Western and Vedic fixtures — verified. Version handling: major-version mismatch throws a typed error; minor/patch mismatch is silently accepted — both confirmed by test.

## 8. Security / Data Governance Findings

No `eval`/`exec`/shell/unsafe deserialization anywhere in `packages/astrology-core/src/`. `deserializeNormalizedChart` does not runtime-validate the parsed JSON's shape beyond the schema-version check — this is a **deliberate, documented** design choice (parse/validate are intentionally separate concerns, matching `calendar-core`'s own "validate only at the boundary" convention), not a silent gap, but it does mean a caller that deserializes untrusted JSON without also calling `validateNormalizedChart()` afterward would propagate malformed data silently. No PII (birth data) is logged anywhere in the reviewed code — error messages embed the *offending value* (e.g., an invalid latitude) into human-readable Vietnamese strings via `AstrologyCoreError.message`/`details`, which is appropriate for a validation-error context but worth remembering if these errors are ever logged to a shared/aggregated log store in a later phase (the birth coordinates would appear in that log). `computeBirthDataFingerprint` uses SHA-256 (Node's built-in `node:crypto`, no new dependency) over calculation-relevant fields only. No secrets, API keys, or credentials exist anywhere in this package.

**Missing test identified and not yet added** (recommend before Phase 3, not added during this audit-only gate per instruction not to add a large new suite unless necessary): a test asserting `serializeNormalizedChart` behavior on a chart containing `NaN`/`Infinity` (currently untested; §3/§7 finding). This is small enough to add in five minutes whenever `dignities[].type` is resolved, and is not "necessary to close a real contract gap" on its own — noted for the next touch of that file.

## 12. Recommended Fixes (for items not fixed during this gate)

- **#2 (CelestialBody)**: adopt `"sun" | ... | "pluto" | "chiron" | (string & {})` — preserves autocomplete for known bodies, genuinely extensible, zero breaking change to existing code (nothing currently constructs a `CelestialBody` literal outside test fixtures).
- **#3 (DignityType)**: change `NormalizedDignityResult.type` from a closed union to `string` (matching `AspectType`'s already-established open pattern in the same file) — smallest possible change, restores consistency with the file's own existing convention, unblocks Phase 4 without a bigger schema rework.
- **#4 (MIN_YEAR/MAX_YEAR)**: rewrite the code comment to state the true rationale ("practical product bound, not an algorithmic one") or remove the bound and trust `isValidCalendarDate`'s own round-trip check exclusively.
- **#5 (fractional seconds)**: either thread the fractional remainder into `Date.UTC`'s milliseconds argument, or narrow `LocalTime.second`'s validated range to integers and say so in the error message.
- **#6 (serialization hardening)**: add one `Number.isFinite` guard loop (or reuse `validateNormalizedChart`) inside `serializeNormalizedChart`, throwing rather than silently emitting `null`.

None of these require touching `BirthData`'s shape, `resolveBirthDataInstant`'s behavior, or any already-passing test's expected value.
