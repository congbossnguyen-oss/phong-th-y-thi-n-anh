# INTERPRETATION AUDIT — Calculation vs Rule vs Interpretation vs AI

Per the brief's Section 7 requirement, every repo's actual data flow was traced in source (not inferred from README) to classify each into: **Calculation** (raw facts, e.g. "Mars = 14° Aries"), **Rule** (deterministic astrological logic, e.g. "Mars in Aries → condition X true/false"), **Interpretation** (natural-language reading text), and **AI generation** (LLM-produced prose). See `AI_ARCHITECTURE_AUDIT.md` for the deep dive on the 3 repos with actual AI/LLM code.

## The central finding (directly answering the brief's Section 7/8 question)

Only **3 of 10** repos contain any interpretation-adjacent code beyond "raw calculated fact." Of those 3:

- **opastro** is the one genuine, fully-realized **Chart → Factors → Rules → Interpretation** pipeline in the entire audited set, verified by execution, with zero LLM anywhere and a working provenance/explainability command. This is the architecture pattern the brief's Section 9 explicitly wants — it happens to already exist, just not commercially reusable as code (AGPL-tainted dependency).
- **astro-natal-chart** and **zodiac-engine** are the two repos with actual LLM integration, and both implement the **weak "Chart→LLM" pattern** the brief explicitly warns against: raw or loosely-structured chart data handed to an LLM with no rules layer constraining or grounding its output, no citation mechanism, and (in zodiac-engine's case) the one piece of genuinely structured data in the codebase is architecturally disconnected from the interpretation pipeline entirely.
- **PyJHora, vedic-calc, mayaastrolib, openastrology-library, jyotish-flutter-library-fork, astrology-engine** all sit at "Calculation + Rules" with either no interpretation layer or a thin, generic, non-personalized, non-per-combination text dictionary — useful as rule-logic references, not as interpretation-architecture references.

## Practical implication for the commercial engine

The brief's target architecture (`Birth Data → Astronomical Calculation → Chart → Factors → Rules → Evidence → Scoring → Interpretation → LLM → Report`) has **no fully-matching precedent** in this audited set, but **opastro's pipeline is the closest real-world validation that the pre-LLM half of that architecture is buildable and works in practice** — its `FactorDetail`/`SectionInsight` typed model, SHA-256-seeded determinism pattern, and `explain` command are all worth deliberately studying (not copying, given the license) when designing the commercial engine's own rule-engine and evidence-engine layers (see `ARCHITECTURE_PROPOSAL.md`).
