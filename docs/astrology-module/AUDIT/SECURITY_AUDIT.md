## Cross-cutting findings

1. **No repo audited implements comprehensive birth-data input validation at the library boundary.** Every repo either has no validation at all (vedic-calc, astrology-engine, PyJHora's `Place` class) or partial validation (openastrology-library's unvalidated timezone string, opastro's unescaped `user_name`). **Whatever calculation engine is chosen, the commercial product must build its own dedicated input-validation/sanitization layer in front of it** — this is not optional, and no audited repo can be trusted to do it for you.
2. **The only repo with a confirmed prompt-injection/XSS vulnerability is zodiac-engine** — directly relevant as a negative example given the target product will also handle user-supplied names and eventually AI-generated narrative text. Any AI-narrative stage in the commercial engine must sanitize LLM output before rendering it as HTML (e.g., with `bleach`) and must never mark model output `| safe`/trusted by default.
3. **Two repos (PyJHora, jyotish-flutter-library-fork) have supply-chain-adjacent risks**: PyJHora's `eval()`-based dispatch and bundled pickle file are low-risk as currently used but would need hardening before reuse; jyotish-flutter's FFI library-loading path needs pinning/checksums in a server deployment.
4. **astro-natal-chart's untrusted precompiled binary** is the single starkest supply-chain red flag in the set — a third-party `.pyd` with zero provenance verification should never be used in production regardless of how well it happened to compute the benchmark chart in this audit.
5. **No repo handles PII (birth data) with any special care beyond ordinary parameter passing** — none encrypt birth data at rest, none apply retention policies, none redact birth data from logs (opastro's own admin-token logging pattern is safe, but this is not a general guarantee across the set). This is entirely the commercial product's own responsibility to design (see `ARCHITECTURE_PROPOSAL.md` data model — birth data should be treated as sensitive PII throughout).

## Recommendation for production

Whichever calculation engine/architecture is ultimately built, budget explicitly for: (a) a dedicated, tested input-validation layer for all user-supplied birth data (date/time/lat/lon/timezone) independent of the underlying ephemeris library; (b) sanitization of any AI-generated or user-supplied free text before it is ever rendered as HTML; (c) sourcing Swiss Ephemeris (or its replacement) via an official, verifiable channel (PyPI `pysweph`/`pyswisseph`, or a from-source build with a known-good checksum) — never a bundled precompiled binary of unverified provenance, as astro-natal-chart demonstrates the risk of; (d) least-privilege CORS/network configuration from day one, since the default configs seen in this audit (zodiac-engine's `allow_origins="*"`) are not production-safe.
